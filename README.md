# 과제 14: 힙 정렬, 퀵 정렬 및 병합 정렬의 성능 비교

## 1. 빌드 및 실행

```
gcc -O2 -std=c11 -o sort_compare sort_compare.c
./sort_compare
```

- 실행 환경: (OS / 컴파일러 및 버전 / CPU를 여기에 기재)
- 데이터 크기: n = 1,000 / 2,000 / 4,000 / 8,000 / 16,000 / 20,000
- 무작위 정수(0~1,000,000, 중복 허용)를 생성하고, 모든 알고리즘은 같은 원본의 복사본을 오름차순으로 정렬한다.
- 각 결과는 `qsort`로 만든 기준 배열과 비교하여 검증한다(오류 시 `[SORT ERROR]` 출력). 모든 실험에서 오류는 없었다.
- `malloc` 실패 시 오류 메시지를 출력하고 종료한다(`xmalloc`).

## 3. 측정 방법

### 3.1 숫자 비교 횟수

- 데이터 값끼리 비교할 때마다 카운터를 1 증가시킨다(`lessThan()` 함수 또는 병합 시 `g_cmp++`).
- 힙 정렬: 힙 구성과 힙 속성 복구(`siftDown`)의 값 비교를 모두 포함한다(두 자식 간 비교 + 부모와 큰 자식의 비교).
- 병합 정렬: 병합 시 `a[i] <= a[j]` 비교를 센다. 한쪽이 소진된 뒤의 나머지 복사는 비교가 아니므로 세지 않는다.
- 퀵 정렬: 분할 과정의 `a[j] < pivot` 비교와 Median-of-Three의 피벗 선택 비교를 포함한다. `for`/`while`의 인덱스 및 종료 조건 검사(`j <= hi`, `i <= mid` 등)는 제외한다. 무작위 피벗은 난수로 위치만 고르므로 값 비교가 없다.
- 기준 배열 생성(`qsort`)과 결과 검증(`memcmp`)은 비교 횟수에 포함하지 않는다(카운터를 정렬 직전에 0으로 초기화).

### 3.2 실행시간

- 고해상도 타이머로 정렬 함수 호출 직전과 직후의 시각 차이를 ms 단위로 측정한다.
- 데이터 생성, 배열 복사, 결과 검증, 출력 시간은 제외한다. 모든 알고리즘에 같은 방법과 단위를 적용한다.
- 안정성을 위해 각 (크기, 알고리즘)마다 **21회 반복**한다. 매회 원본에서 새로 복사한 배열을 정렬하고, 보고하는 값은 **중앙값**이다(1회성 지연이나 이상치의 영향을 줄이기 위함). 무작위 피벗의 시드도 매회 같은 값으로 초기화하여 비교 횟수가 항상 같도록 한다.

### 3.3 메모리 사용량

**(1) 이론적 보조 공간(Auxiliary Space)** — 알고리즘 자체의 성질이며 컴파일러와 무관하다.

| 알고리즘  | 보조 공간                            |
| --------- | ------------------------------------ |
| 힙 정렬   | O(1)                                 |
| 병합 정렬 | O(n) (임시 배열)                     |
| 퀵 정렬   | 평균 O(log n), 최악 O(n) (재귀 스택) |

**(2) 바이트 단위 값은 실측이 아니라 계산한 추정값이다.** 표의 Memory는 프로파일링 도구로 측정한 값이 아니며, 아래 모델로 계산한 값이다. 원본 데이터 배열은 공통 비용이므로 제외한다.

모델의 가정:

1. `lessThan`, `swapInt`처럼 작은 `static inline` 함수는 `-O2`에서 인라인되므로 별도 프레임을 계산하지 않는다.
2. 스택 프레임 = 매개변수 + 지역변수 + 반환 주소(8B), 64bit 기준이다. 정렬(padding), 저장된 레지스터, 컴파일러의 레지스터 할당은 고려하지 않는다.
3. 정렬 도중 가장 깊은 시점에 스택에 동시에 쌓인 (인라인되지 않은) 함수들의 프레임을 합하고, 별도로 할당한 배열을 더한다.

| 함수                        | 계산                                        | 크기 |
| --------------------------- | ------------------------------------------- | ---: |
| `heapSort(int*, int)`       | (8+4) + 지역 `i` 4 + 반환 8                 |   24 |
| `siftDown(int*, int, int)`  | (8+4+4) + 지역 `tmp`, `child` 4+4 + 반환 8  |   32 |
| `mergeSort(a, tmp, lo, hi)` | (8+8+4+4) + 지역 `mid, i, j, k` 16 + 반환 8 |   48 |
| `quickSort(a, lo, hi)`      | (8+4+4) + 지역 `m, pivot, i, j` 16 + 반환 8 |   40 |

- **힙 정렬**: 재귀가 없으므로 `heapSort → siftDown` 두 프레임의 합 24 + 32 = **56 Byte**(n과 무관).
- **병합 정렬** = 임시 배열 `n × 4` + (최대 재귀 깊이 + 1) × 48.
- **퀵 정렬** = (최대 재귀 깊이 + 1) × 40 (보조 배열 없음).
- 최대 재귀 깊이는 실행 중 `g_depth`로 추적한 `g_maxDepth`이며, 실제로 분할/병합을 수행하는 호출(`lo < hi`)만 센다. 가장 깊은 호출은 항상 `lo >= hi`로 즉시 반환하는 호출을 하나 더 호출하므로 그 프레임 1개를 위해 **+1**을 더한다.

**한계**: 실제 스택 사용량은 컴파일러와 최적화 수준에 따라 달라진다. 별도 확인에서 `-O0`에서는 프레임이 이 모델보다 컸고(재귀 함수 약 2배), `-O2`에서는 힙 정렬이 더 작고(`heapSort`가 인라인됨) 병합 정렬의 프레임은 더 크게(호출당 약 75~80 Byte) 나타났다. 따라서 바이트 값은 알고리즘 간의 **상대적 크기와 증가 경향**을 비교하는 용도이며, 절대값으로 해석하지 않는다.

## 4. 비교·분석

### 4.1 데이터 크기 증가에 따른 비교 횟수

- n이 2배가 될 때마다 비교 횟수는 힙 정렬 16,814 → 37,634 → 83,364 → 182,727 → 397,532(매번 약 2.18~2.24배), 병합 정렬 8,717 → 19,401 → 42,801 → 93,691 → 203,299(약 2.17~2.23배)로, 2배보다 조금 더 증가한다. 이는 O(n log n)의 전형적인 증가 양상이다.
- n = 20,000에서 n·log₂n ≈ 285,754이다. 병합 정렬은 260,968(약 0.91배), 퀵 정렬은 319,749~348,007(약 1.12~1.22배), 힙 정렬은 510,737(약 1.79배)이다. 힙 정렬의 비교 횟수는 병합 정렬의 약 1.96배이다.
- 병합 정렬은 두 정렬된 부분을 합칠 때 한쪽이 먼저 소진되면 나머지를 비교 없이 복사하므로 비교 횟수가 이론적 최소치에 가깝다. 힙 정렬은 `siftDown`에서 한 단계마다 "큰 자식 선택"과 "부모와 비교" 두 번을 비교하고, 정렬 단계에서 루트에 놓인 마지막 원소가 대부분 바닥 근처까지 내려가기 때문에 비교 횟수가 병합 정렬의 약 2배가 된다. 퀵 정렬은 피벗 하나당 구간 전체를 훑는 방식이라, 피벗이 완벽한 중앙값이 아닌 만큼 병합 정렬보다 비교가 많다.

### 4.2 실행시간 차이

- n ≥ 2,000에서 **병합 정렬이 가장 빨랐다**. n = 20,000에서 병합 정렬 0.756ms, 퀵 정렬 1.086~1.150ms, 힙 정렬 1.102ms이다. 병합 정렬은 힙 정렬보다 약 30~40%, 퀵 정렬보다 약 12~35% 빨랐다.
- 병합 정렬이 빠른 이유는 비교 횟수가 가장 적고(힙 정렬의 약 절반), 임시 배열로 복사하고 되돌려 쓰는 과정이 연속된 메모리를 순차적으로 접근하기 때문으로 보인다. 즉, 복사 비용이 추가되어도 이 실험에서는 비교 횟수 감소와 순차 접근의 이점이 더 컸다.
- 힙 정렬은 비교 횟수가 병합 정렬의 약 2배이고, `2·root+1`처럼 멀리 떨어진 원소를 접근해 캐시 효율이 낮을 수 있다. 이번 실험에서 병합 정렬보다 느린 것과 방향은 일치하지만, 캐시가 원인이라고 확정할 수는 없다.
- 퀵 정렬과 힙 정렬은 가까운 수준이다. n = 2,000~8,000에서는 퀵 정렬이 힙 정렬보다 약 13~29% 빨랐으나, n이 커질수록 차이가 줄어 n = 16,000~20,000에서는 거의 같았다(힙 0.870/1.102ms, 퀵 0.830~0.906/1.086~1.150ms).
- 이 순위(병합 < 퀵 ≈ 힙)는 컴파일러, CPU, 최적화 수준에 따라 달라질 수 있다. 특히 퀵 정렬과 병합 정렬의 순위는 환경에 민감하므로, 이 결과를 모든 환경으로 일반화하지 않는다. n = 1,000에서는 모든 값이 0.1ms 이하로 작아 우열을 판단하지 않는다.

### 4.3 메모리 사용량 차이

- 힙 정렬은 56 Byte로 n과 무관하다(제자리 정렬, 재귀 없음). 이론적 보조 공간 O(1)과 일치한다.
- 병합 정렬은 임시 배열 때문에 n에 비례해 증가하며(4,528 → 80,768 Byte), 전체의 약 99%가 임시 배열(n × 4)이고 재귀 스택은 작다(예: n = 20,000에서 80,000 + 16×48 = 80,768). 병합 정렬의 재귀 깊이는 10~15로 ⌈log₂n⌉과 같다.
- 퀵 정렬은 재귀 스택만 사용하며 640~1,400 Byte로 매우 작다. n이 20배 늘어도 약 1.1~1.7배만 증가한다(재귀 깊이가 log n에 가깝게 증가).
- 퀵 정렬의 재귀 깊이는 n = 20,000에서 25~32로, log₂n ≈ 14.3의 약 2배이다. 이는 평균 O(log n) 스택 공간(최악은 O(n))과 같은 증가 경향이다.
- 정리하면 메모리는 힙 정렬 < 퀵 정렬 << 병합 정렬 순이다. (모두 계산값이다.)

### 4.4 퀵 정렬 피벗 선택 방법에 따른 차이

- **비교 횟수**: Median-of-Three가 모든 크기에서 가장 적었다(n = 20,000: First 348,007 / Random 320,278 / Median3 319,749). 극단적으로 치우친 분할을 피하기 때문이다. n = 16,000에서는 First 대비 약 10% 적다. Random은 First보다 많을 때(n = 1,000, 4,000, 8,000)와 적을 때(n = 2,000, 16,000, 20,000)가 섞여 있어, 난수에 따라 결과가 달라진다. 이번 실험은 시드 하나만 사용했으므로 Random의 우열은 일반화하기 어렵다.
- **재귀 깊이와 메모리**: Median3가 모든 크기에서 가장 작았다. n = 20,000에서 깊이는 First 32, Random 29, Median3 25이며(메모리 1,320 / 1,200 / 1,040 Byte), 분할이 더 균형 잡혔음을 보여 준다. Random은 n = 4,000, 8,000에서 깊이 32로 First(26, 30)보다 깊었고, n = 16,000에서는 반대로 First(34)보다 얕았다(32).
- **시간**: Random이 모든 크기에서 가장 느렸다(First 대비 약 1~18%). 난수 생성(`xorshift32`와 나머지 연산) 비용이 매 분할마다 추가되지만, 무작위 데이터에서는 분할 품질이 좋아지는 이득이 없기 때문으로 보인다. First와 Median3는 서로 −12%~+4% 이내로 비슷하다. Median3는 비교 횟수가 가장 적지만 피벗 선택 비교가 추가되므로 시간 이득이 크지 않다.
- 이번 데이터는 무작위라서 First Element의 최악 경우(이미 정렬된 입력 등 → O(n²), 재귀 깊이 n)가 나타나지 않았다. 따라서 "First가 충분히 빠르다"는 결과는 입력이 무작위일 때에 한정된다. Random과 Median3는 입력 순서에 덜 민감하다는 장점이 있다.

### 4.5 시간·공간 복잡도

| 알고리즘  | 최선       | 평균       | 최악       | 추가 공간                            |
| --------- | ---------- | ---------- | ---------- | ------------------------------------ |
| 힙 정렬   | O(n log n) | O(n log n) | O(n log n) | O(1)                                 |
| 병합 정렬 | O(n log n) | O(n log n) | O(n log n) | O(n)                                 |
| 퀵 정렬   | O(n log n) | O(n log n) | O(n²)      | 평균 O(log n), 최악 O(n) (재귀 스택) |

- 실험에서 비교 횟수의 증가(약 2.2배/2배)와 메모리 경향(힙 상수, 병합 선형, 퀵 로그에 가까움)이 위 표의 이론과 일치한다.

### 4.6 알고리즘별 장단점

| 알고리즘  | 장점                                                                                                | 단점                                                                                                                                      |
| --------- | --------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| 힙 정렬   | 최악에도 O(n log n) 보장, 추가 메모리 O(1)(모델 계산 56 Byte 고정)                                  | 비교 횟수가 가장 많음(병합의 약 2배), 이번 실험에서 n ≥ 2,000에서 병합보다 약 30~40% 느림, 불안정 정렬                                    |
| 병합 정렬 | 비교 횟수가 가장 적음, 입력과 무관하게 O(n log n), 안정 정렬, 이번 실험에서 n ≥ 2,000에서 가장 빠름 | 임시 배열 O(n) 필요(n = 20,000에서 약 80KB)                                                                                               |
| 퀵 정렬   | 제자리 정렬로 추가 메모리가 매우 작음(재귀 스택만), 이번 실험에서 힙 정렬과 비슷하거나 더 빠름      | 최악 O(n²)(피벗이 나쁠 때), 불안정 정렬, 병합보다 비교 횟수가 많고 이번 실험에서 더 느림, 피벗 선택 방법에 따라 성능과 재귀 깊이가 달라짐 |

## 5. 결론

- 비교 횟수: 병합 < 퀵 < 힙
- 실행시간(이번 실험, n ≥ 2,000): 병합이 가장 빠르고, 퀵과 힙은 비슷함 (n이 클수록 퀵과 힙의 차이는 줄어듦)
- 메모리(계산값): 힙(상수) < 퀵(로그 수준) << 병합(선형)
- 퀵 정렬 피벗: Median-of-Three가 비교 횟수와 재귀 깊이(메모리) 모두 가장 작고, Random은 시간이 가장 느렸음
- 최악 경우를 보장하면서 추가 메모리가 거의 없어야 한다면 힙 정렬, 메모리가 충분하고 안정 정렬과 일정한 성능이 필요하다면 병합 정렬, 메모리가 작고 입력이 무작위에 가깝다면 퀵 정렬이 적합하다.
